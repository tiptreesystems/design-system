## 1. Current state (corrected)

- **Repo topology:** tasc-stack is a **meta-repo of ~16 git submodules** — `frontend`, `platform-frontend`, `docs`, and every service are separate GitHub repos (`tiptreesystems/*`). Any dependency bump in a frontend = PR in that repo + a tasc-stack submodule-pointer PR. Tooling must handle both.
- **Render stacks:** Lacuna (10.4k-line f-string Flask monolith + growing `flask_site/` layer), Althea (three render paths: client vanilla-JS SPA; **Node build-time prerendered marketing partials** — `scripts/prerender.js` renders hashed HTML that FastAPI fetches, so these pages are *not* Python-rendered; Python f-string utility pages), React/Tailwind platform console (production deployment unconfirmed — `@theme` color mappings are commented out, only local Vite scripts exist), Astro docs (legacy), Next.js hub (docs-new).
- **Theme conventions conflict:** hub is dark-default with `[data-theme='light']`; Lacuna is **light-default** with `[data-theme="dark"]`; Althea is light-only with no theme attribute; console uses a `.dark` class. A naively dropped-in hub `:root` would flip Lacuna dark.
- **Token overlap is near zero — and where names DO overlap they collide:** Althea defines 332 tokens; only ~5 names overlap with the hub's, and the worst overlap is a direct conflict — Althea's `--color-accent` is iOS blue `#007aff` while the hub's `--color-accent` is brand teal. If both stylesheets ever coexist, import order silently decides which wins. Lacuna's CSS depends on `--bg-body`/`--brand-primary` etc. that no proposed contract supplies. Renaming is a migration project, not a swap. (Althea's own "legacy semantic aliases" block shows the alias pattern already works there.)
- **Brand drift is real and reaches beyond CSS:** `#47696b` appears *nowhere* in Lacuna; `#4a7c7c` appears 54 times under the `lacuna/` package (counting scope: whole tree, case-insensitive) — across 5 Python files (including pipeline prompt templates and renderers: `stage_16_article_video/prompt.py`, `stage_17_article_viz/prompt.py`, `stage_16_article_video/render.py`) and **9 SVG assets** (logos/illustrations). The SVGs matter: correcting the drift means re-exporting brand assets, *unless* Lacuna's teal is a deliberate sub-brand — a designer ruling needed before anyone "fixes" it. Already-generated media never retro-fixes; the planned `tokens.py` must feed the pipeline prompts so *future* artifacts are on brand.
- **The chat widget is an intentional fork, not a stale copy:** of the 59 regular vendored files (the tree also carries documentation symlinks), 38 differ, 15 are identical, 6 are Lacuna-only (panel shell, tabs/drafts). Divergence runs both directions (Lacuna added mentions/drafts; upstream added wake modes). Pinning Lacuna to an upstream build would delete product features.
- **docs-new's tokens are the best starting point but need repair before extraction:** duplicate `--stone-150`/`--stone-950` declarations; the showcase parser keeps the *first* declaration while browsers apply the *last*, so the showcase can display wrong values; `--stone-50` vs `--stone-050` inconsistency; the vitest token tests exist but **no CI runs them**; font variables (`--font-inter`, `--font-literata`) are injected by next/font and don't exist outside Next.

## 2. End-state architecture

**Principle: framework-agnostic. The cross-platform canon is typed tokens + component intent (purpose, variants, states, accessibility outcomes); CSS + DOM/ARIA specs are the canonical *web* implementation of that intent; SwiftUI is the canonical *Apple* implementation (iOS consumer confirmed — see §4.7/§7).** On the web, the contract is more than CSS: a versioned component contract comprises DOM anatomy (element choice, structure, slots), semantics/ARIA, states, events, keyboard behavior, and the `.tt-*` classes + tokens that style it — CSS cannot express element choice or focus management; web bindings implement the full contract and are conformance-tested against it. Swift does not translate CSS or ARIA — it implements the same component intent with native controls, native accessibility (VoiceOver, Dynamic Type), and generated native tokens.

```
LAYER 0  tokens        namespaced --tt-* API (brand, ramps, semantic, type, radius, motion)
LAYER 1  tt.css        .tt-* classes — the canonical visual layer
LAYER 1b specs/        versioned component contracts (DOM, ARIA, states, events, keyboard)
LAYER 2  behavior JS   self-contained, same-origin web components / ES modules
─────────────────────────────────────────────────────────────────────
ADAPTERS (per consumer): theme adapter (data-theme ↔ .dark ↔ light-only),
  alias sheet mapping legacy token names → --tt-* during migration
BINDINGS (per stack, conformance-tested against specs/):
  tiptree_ui (Python)  → Lacuna server pages; docs-new post-conversion (§4.7)
  vanilla JS           → Althea SPA + prerender pipeline
  (NO React bindings — decided 2026-07-20: Lacuna and Althea are permanently
   non-React, docs-new converts to Python, so the end state has no React
   consumer. The hub consumes tokens-only while it remains Next; the console's
   Tailwind adapter exists only if the console survives its §7 decision.)

DESIGN PRINCIPLE — server-first, progressively enhanced: every component must be
fully functional and correctly styled as pure HTML+CSS (Lacuna serves crawlers
with no JS runtime guaranteed); behavior JS enhances per component, never gates
rendering or content. The behavior layer is load-bearing, not optional — it is
the ONLY way interactive components reach both permanent contexts (server-rendered
Python pages and the vanilla-JS SPA), which raises experiment C's stakes and
reweights the rubric: the React consumption seat drops to near-zero; no-JS
degradation and SSR-compatibility move up; experiment E candidates are viable
only if their CSS stands alone without a framework runtime.
```

**Namespacing is mandatory.** The portable API is `--tt-*` prefixed. Existing token names in every app keep working via generated per-consumer alias sheets (`--brand-primary: var(--tt-color-accent)`), migrated reference-by-reference with light+dark visual-regression checks before any legacy name is deleted. **No wholesale `:root` replacement, ever.**

**Home (decision required — recommendation changed in v2):** a **dedicated `design-system` repo** rather than a package inside docs-new. The v1 argument (designer keeps their environment) is weakened by reality: docs-new has no workspaces, no publishing, no CI, no release automation — all of that must be built regardless, and building it in a repo whose identity is "the docs site" muddies ownership, release cadence, and credentials. The designer's loop is preserved with a minimal showcase in the design-system repo driven by a single command (`npm run dev`: watch tokens → regenerate CSS → refresh) for day-to-day authoring, while the hub's rich `/design-system` pages remain the polished documentation surface, consuming published versions. Alternative if the designer strongly objects: convert docs-new into a proper release monorepo (workspaces, package CI, CODEOWNERS boundary, no consumer imports from internal paths). Pick one explicitly; don't drift into either.

**Consumer scope (updated 2026-07-23):** in scope — **Althea (frontend), Lacuna, the docs site (the updated `docs` repo — final stack and owner to confirm with Martin/Ivan), and platform-ios**. **docs-new is RETIRED (being deleted)** — the docs repo has been updated and supersedes it; docs-new's roles transfer as follows: token provenance is historical (the seed was extracted and designer-curation happens in the design-system repo now), the §4.8 conversion track is moot, and the slice's static-composition recipe (compose from manifest → content-hashed file → one link) is portable to the updated docs repo as-is. **This also removes the estate's last Next.js surface** — the end-state render styles are now exactly the two permanent ones (Python HTML + vanilla JS) plus the console pending its fold decision. Excluded pending §7 decisions — the platform console (platform-frontend); its rows below are conditional. **Normal consumption is `primitives.css` + exactly one theme file + selected component files;** `tokens.css` survives only as a dark-default backward-compatibility composition (correct for the hub; wrong for light-only/light-default consumers — Althea and Lacuna must import `themes/light-default.css`, never `tokens.css`).

## 3. Policies the contract ships with

- **Versioning & rollback:** SemVer with defined semantics — token *value* changes: patch/minor; class or DOM-contract changes: major with a deprecation window (old + new coexist behind aliases); behavior JS versioned in lockstep from the same release tag as tt.css and all bindings (single version train; no compatibility matrix to start — one number everywhere). **All bindings live in the design-system repo and ship from the same tag** — including the `tiptree-ui` wheel — so "who fixes bindings when a spec changes" has one answer: the contract-changing PR does, with the binding owner as required reviewer, in one repo. **Light+dark visual regression is part of the release gate**, not just migration. Canary + rollback documented per consumer — with the honesty that **neither rollback mechanism exists yet and both are prerequisites**: Althea's `upload_assets.py` today overwrites a single mutable `manifest.json` with no retained history (prerequisite: immutable manifest snapshots + an atomic "current" pointer), and Lacuna deploys only `lacuna-wiki:latest` (prerequisite: images tagged by commit/digest and retained). Both get exercised in the rollback drill before anything publishes. Changelog per release.
- **Theming & overrides — "override values, never rules":** the generator emits **explicit theme-polarity files, and every consumer selects exactly one** — `primitives.css` (polarity-free base tokens) plus `themes/light-default.css`, `themes/dark-default.css`, and an explicit-selector-only variant. No single blessed `:root` polarity: dark-on-`:root` fits only the hub; Lacuna is light-default, Althea light-only, the console uses `.dark`. Per-consumer adapters map attribute conventions where they differ. **Sub-brands are sanctioned the same way dark mode works — as token-value overrides living IN the design-system repo** (e.g. `themes/lacuna.css` setting `--tt-color-accent` etc. under a `[data-brand]` attribute), designed, versioned, and screenshot-verified like everything else. The designer controls the **themeable surface**: an explicit short list of tokens sub-themes may override (accent, serif voice, surface tint); identity-level tokens (spacing scale, type ladder, focus rings) are locked. What is *never* sanctioned: redefining `.tt-*` component rules or raw values inside an app — that's drift with extra steps, and the CI guardrails make it fail the build. This is where the "Lacuna teal: drift or sub-brand?" ruling lands: if sub-brand, it becomes `themes/lacuna.css`, not preserved app-local CSS.
- **CSS coexistence contract (namespacing is necessary, not sufficient):** `--tt-*`/`.tt-*` prevents *name* collisions but not cascade collisions — Althea's `base.css` styles bare `button`/`input`/`select` globally, and its overlays sit at `z-index: 10000+`, so a light-DOM `.tt-btn` dropped into that page inherits hostile rules immediately. The package therefore ships with: **dual cascade entries** — the default build is *unlayered* component CSS (class selectors beat legacy bare-element rules by normal specificity, no consumer changes required), plus an optional `@layer tt`-wrapped entry for consumers whose whole cascade is layered (unlayered author CSS outranks any named layer, so layer-wrapping is only safe where the host has layered its own styles — Althea today has not); a specificity ceiling; **no global resets and no bare-element selectors** — the package styles opt-in classes only, and documents which inherited properties (typography, form-control appearance) it normalizes *within* its classes; a **shared z-index scale and portal/overlay policy** mapped against each app's existing stacks; **sanctioned extension points** — documented modifiers, slots, and per-component custom properties — plus a **documented exception process** for legitimate product-specific layout and emergency fixes ("override values, never rules" needs an escape hatch that isn't a hack); and **hostile-host test fixtures** for the experiments — components mounted inside Althea's real global-CSS environment, with experiment C comparing light DOM vs shadow DOM where isolation earns its cost.
- **Fonts:** the contract owns font *role tokens* (`--tt-font-sans`, `--tt-font-serif`, `--tt-font-mono`). Binaries: package ships licensed, subsetted WOFF2 (Inter + Literata, both OFL — license files included) as optional assets with correct MIME/cache guidance; consumers either use them or bind the role tokens to their own hosting. Never assume next/font variables exist outside the hub. Althea's esbuild `publicPath` quirk means font URLs must be verified in its pipeline specifically. **Media pipelines are a separate font consumer:** browser WOFF2 files do nothing for Manim/Pango — Lacuna's GPU worker image installs no fonts at all today — so every media-worker image gets renderer-compatible TTF/OTF installs plus a font-availability smoke test.
- **Security:** behavior artifacts are self-contained and same-origin (no esm.sh/CDN imports — Lacuna's current import map gets absorbed into the bundle); CSP profiles documented per host; Python bindings use `markupsafe` escaping, attribute allowlists, and URL validation, with injection tests alongside snapshot tests.
- **Performance & payload (load speed is THE product priority for Lacuna, marketing, and docs — SEO/AEO/GEO correlate):** the package is published as **per-component CSS files** (plus an optional generated full bundle for the showcase/tests), and **the serving unit is one composed, content-hashed file per loading boundary** — Althea marketing (`public.css`) and Althea app (`app.css`) are two boundaries, Lacuna is one precomposed subset, the hub keeps tokens-global + component-leaf imports. Measured baselines (2026-07-20): Althea `public.css` 146,918 B raw / 21,080 B brotli, `app.css` 237,600 B / 29,324 B; **Lacuna inlines 77,523 B of CSS into every HTML response** (verified) — uncacheable by design, re-sent per page, which is the number the external-cached model must beat and the integration branch must prove. **Dependency rule: every component requires the token layer — `primitives.css` plus exactly one selected theme file — and its own component file; nothing else.** No preemptive shared `core.css` (it becomes a monolith seed); shared values live in tokens, shared primitives get extracted only when repeated production code proves them. (`tokens.css` survives as a back-compat composition of primitives + dark-default.) **Lacuna's composed-subset URLs are content-hashed, not merely version-stamped** — the subset can change without a package version change, and immutable headers demand the URL change with the content. **Budgets are consumer-level as well as library-level:** CI budgets every component file, tokens, the optional full bundle, and each real consumer composition — the library's own size can never stand in for actual page cost. The mechanism is **selective per-component imports composed by each consumer's bundler** (Althea's esbuild entry sheets, the hub's Next layout import) — note that *no pipeline here removes unused rules automatically*; what you import is what you ship, so the budgets below are measured against real composition, not assumed dead-code elimination. For Lacuna, the primary mechanism is a **curated import list** in the wheel integration; registry-derived automatic subsetting is a conditional future upgrade *only if* bindings become the sole render path (raw `.tt-*` markup in f-strings is invisible to any binding scan, so enumeration is unsound until then). **Size budgets enforced in CI as a release gate, with numbers and methodology fixed at scaffold kickoff** (indicative: tokens.css ≤ 3 KB brotli / ≤ 12 KB raw; core component sheet ≤ 12 KB brotli / ≤ 50 KB raw; measured at brotli `-q 11`, raw bytes tracked alongside; fonts and `themes/*.css` excluded and budgeted separately); a budget regression fails the release. Versioned assets ship `Cache-Control: public, max-age=31536000, immutable` (HTML responses are never immutable) — stamped URLs are what make that header safe, and together they mean the stylesheet is fetched once and warm-cached across every subsequent page — note Lacuna currently *inlines* its app-shell CSS into every HTML response (the vendored chat CSS is already external links), so moving to a cached external sheet should make repeat pages faster. Sequencing honesty: the **integration branches measure coexistence cost and budget compliance** (inline CSS + DS sheet together); the inline→external win itself is measured at the §4.6 Lacuna migration, not before. **Fonts are the dominant payload, not component CSS** — subsetted WOFF2, `font-display: swap`, preload hints are part of the font policy above. Web components (experiment C) and the themed-existing-library option (experiment E) carry extra weight (JS before render; inherited bloat) — priced explicitly in their experiments in §5.
- **Enforcement is CI, not convention:** the design-system repo gets required CI from day one — schema-validated token source (duplicates/unknowns rejected), generated CSS diffed against browser-resolved values, a real no-raw-hex/no-raw-spacing lint **scoped to component and binding CSS** (the token source and `themes/*.css` are exactly where raw values legitimately live), the ported vitest decision tests, and binding conformance fixtures.

## 5. Experiments (reworked — real consumers, weighted rubric)

Same pilot set, same extracted tokens, built as **integration branches in the real apps with production builds** — not standalone demos. Coexistence with existing CSS, CSP constraints, and each app's actual pipeline are part of the test.

- **Pilot set:** Button (including the link-vs-button anatomy question), a form control with validation states, Callout, Card (new spec — none exists in docs-new), and **Modal** (focus trap, Escape, scroll lock, inert background, SSR behavior — the honest test of the behavior layer). If web components are on the table for chat, add a small chat vertical slice with events + SSE.
- **A — CSS contract:** hand-authored spec markup from a Lacuna f-string page, an Althea component, and a hub page.
- **B — Python bindings** over A, in a real `flask_site/` page, with injection + conformance tests.
- **C — Web components**, light-DOM, same-origin bundle; explicitly evaluate pre-upgrade semantics/FOUC and prerender/hydration behavior in Althea.
- **D — Generated bindings** (B without the duplication): make `specs/` machine-readable — a `contract.json` companion per spec (variants, states, class maps) plus golden fixtures — and *generate* the Python/JS helpers from them instead of hand-writing either. **What's always safe to generate regardless of D's outcome:** token constants, enums, class-name maps, theme adapters, conformance fixtures, package exports. **The kill criterion, verbatim:** *if a component generator needs embedded Python/JS code snippets to express a component, stop generating that component — the schema has become an inferior programming language.* Also killed if generated-code debugging measurably slows the pilot. Stateful components (Modal, Tabs, focus management) are hand-written and conformance-tested in every outcome.
- **E — Theme an existing CSS library** instead of authoring `tt.css`: re-skin a mature, accessibility-hardened base with our tokens and price it against hand-authoring. Kill criteria: if pixel-matching the designer's spec requires fighting the base's opinions, or the post-subset payload exceeds the CI budget, author `tt.css` clean.
- **F — Fragment/iframe embedding for chat: extracted to a separate chat-architecture RFC, not run against the pilot set.** Honesty about the premise: iframe-isolated chat is a *hypothetical* architecture, not the current deployment pattern — today's iframes host *generated widget content* with `sandbox="allow-scripts allow-forms"` (no `allow-same-origin`), while the chat shell lives outside them and its SSE uses credentialed EventSource. An iframed chat must therefore prove cookie/CORS behavior, SSE, auth refresh, parent↔frame messaging, CSP, failure handling, and theme transfer — or design a token/postMessage auth protocol. That's an RFC-scale question with its own criteria, and it can't score on the Button/Card pilot set anyway.
- **Staged funnel (not six parallel bets):** **A is the baseline** — built first, everything scores against it. **B and C run the full pilot set** on top of A. **D builds one complex component** (the Modal) and compares directly against B's hand-written version — enough to price generation without generating everything. **E names one candidate library at kickoff** and re-skins two representative components (Button + Modal) to price make-vs-buy — not a full parallel build. **F is the separate chat RFC** above. Same tokens throughout, so every option scores on identical ground.
- **Rubric (weighted, pass/fail thresholds agreed before running):** designer authoring loop; consumption ergonomics per seat; drift resistance; correctness enforcement (where ARIA/anatomy is guaranteed — and specifically: what enforces the contract for consumers *without* bindings, since pure Experiment A has no enforcement story); testability in CI; migration cost measured on the real branch; **per-app shipped payload after subsetting** (against the CI budgets) plus before/after **Lighthouse lab runs** on each integration branch under a fixed browser/device/network profile (real Core Web Vitals are field data — collected only during a production canary after the winner ships, never claimed from lab runs); no-JS degradation (Lacuna is a server-rendered wiki — custom elements without JS are dead weight there); per-seat light+dark verification; what a breaking change looks like under each API; bus factor.
- **Decision mechanics:** Martin owns the decision, made against the rubric within an agreed window after the branches land. **Before any branch is built**, fix the numbers: scoring weights per rubric line, numeric thresholds (bundle-size deltas, authoring task-time, accessibility-violation counts, visual-diff tolerance, Lighthouse lab scores), the lab profile they're measured under, and a tie-break rule. Kill criteria named up front — e.g., if C's pre-upgrade FOUC or prerender behavior fails in Althea, web components lose the interactive tier; if B's bindings can't beat hand-authored markup on the form control, bindings wait until the contract stabilizes.
- **Framing:** a CSS layer exists in every outcome (the browser only speaks CSS). The experiments decide the *contract surface* (documented markup vs bindings vs custom elements), which tiers get bindings first, and whether web components earn the interactive tier — treat "A as canon" as the hypothesis to falsify, not the verdict. The chat vertical slice exercises the *bundle* path; iframe isolation for chat is deliberately deferred to the F RFC rather than smuggled in as a test condition.

## 6. Governance & designer experience

**Scope split for the build-out — we architect the framework; the designer fills it with design.** Engineering's deliverable is the *machinery*: repo scaffold, token schema + generator, CI/release automation, alias-sheet mechanism, per-consumer integration points (esbuild import, Tailwind adapter, Lacuna wheel + Blueprint + stamped URLs), the preview-screenshot pipeline, bump bots, binding harnesses with conformance rigs, the showcase shell, and the designer guide. The *content* — token curation judgments, component visual design, tt.css authoring, the teal/sub-brand ruling, sage's fate, visual acceptance — is the designer's. **The designer never greps repos and never runs the machinery:** engineering generates the cross-repo CSS inventory and a **classification registry** for every legacy token/value (`shared-alias` / `app-local` / `runtime` / `deprecated` / `ignored`), with automated mapping proposals; the designer's audit role is *ruling on the flagged questionable equivalences* (is Lacuna's `--brand-primary` the same concept as `--tt-color-accent`?), not producing the inventory. Releases are engineering-owned end to end — the designer approves; engineering cuts. The handoff interface: a repo where editing a token shows up in the showcase (and, once consumers are onboarded, in real-app preview screenshots) with one command, plus wired-but-empty slots (tt.css, specs templates, the classification registry's judgment queue) to fill.

**Ownership is joint, split along the visual/semantic line** (a designer should never be on the hook for ARIA or event contracts):

- **Designer owns:** tokens, visual CSS (tt.css), canonical examples, and visual acceptance — required CI enforces their decisions (accent-stays-teal, heading register, no-raw-hex), moving enforcement from convention to build failure.
- **Engineers own:** semantic anatomy (DOM/element choice), accessibility, keyboard/event behavior, bindings, and releases.
- **Joint review** whenever a visual change affects markup: the contract-changing PR fixes its bindings in the same repo, with the binding owner as required reviewer; designer + binding owner ship from the same release.
- Apps consume pinned versions; changes arrive as bump PRs (frontend repos + tasc-stack pointer PRs, bot-managed). "Change once, trickle everywhere" honestly means: one source edit, one release, N reviewable bump PRs — never silent propagation.

**Designer experience commitments:**

- **One command.** `npm run dev` in the design-system repo watches token-source changes, regenerates the CSS, and refreshes the showcase. The designer never runs or understands the generator — the earlier "no build step" framing was a contradiction (tokens.css is generated); the honest promise is *one command, zero pipeline knowledge*.
- **In-context preview across apps** *(activates once integration branches exist — during the scaffold phase the preview covers the showcase only)*. The designer sees what their token change does to real Lacuna and Althea pages *before* merge, without ever running those apps. **Scoped honestly:** onboarding each consumer into the screenshot rig is a separate engineering deliverable per app (checkout credentials, unpublished-artifact injection, pinned consumer commits, deterministic data/auth fixtures, browser infra, baseline ownership, a flake policy — none of which exists today). Every PR runs the fast package checks + showcase screenshots; the real-app screenshot matrix runs small on release candidates (each app in its *supported* theme modes only — Althea is light-only) with the broader matrix scheduled, not per-PR.
- **A one-page designer guide** ships with the scaffold: how to change a token, add a component's visual spec, read the preview screenshots, and approve a release (engineering cuts it). This architecture plan is the engineers' document; it must not become the designer's operating manual.
- **Documentation is a deliverable, not residue — for developers AND agents.** The repo carries: `CLAUDE.md` (source-of-truth map, invariants, ownership, agent hard fences — every future agent session self-briefs from it), `docs/ADDING_A_COMPONENT.md` (the seven-step contribution recipe, including the never-pick-a-winner-silently rule for cross-app consolidations), `docs/DECISION_LEDGER.md` (append-only scope/decision record), and this plan vendored as `docs/PLAN.md` on push (the README's workspace-relative link breaks otherwise). Per consumer, each adoption PR must also update that app's own `CLAUDE.md`/docs with its integration recipe (how it imports, its component manifest, its rollback commands) — the integration knowledge lives where the app's developers look, not only in the design-system repo. **Component refactor order (evidence-based, 2026-07-20):** Button (slice seed) → **Badge/Tag** (exists in all three surfaces as Lacuna `.tag` / Althea `.badge` / docs-new `Badge` — stateless, ~30 lines, one designer reconciliation = low-stakes rehearsal of the ruling workflow) → **Card shell** (surface only: bg/border/radius/shadow/hover — innards stay app-local) → Callout/Tip → Modal reserved for the API experiment, never an early refactor.
- **(Optional, later) Figma variables sync** from `tokens.json`, so design exploration can happen in Figma against the live palette — not required for this designer (who works code-first), but it derisks future designer hires.

## 8. What "done" looks like

Changing a brand color = one token edit, one release, merged bump PRs — no grep, no hand-edits, no drift, and a documented rollback if it goes wrong. A new repo joins by installing one package. The designer ships visual changes without touching app code; CI — not convention — keeps every surface on brand; and every binding is conformance-tested against a contract that covers behavior and accessibility, not just pixels. One honest scope limit: *generated* artifacts (rendered videos, images) capture the palette at render time — `tokens.py` feeding the pipelines keeps future output on brand, but already-rendered media stays as it is.
